# 03 · 实施路线

## 1. 排序依据

参考架构给出的采纳顺序（[reference/implementation_recommendations.md](reference/implementation_recommendations.md)）是：

> 交互引擎 → 工具接口 → **尽早**加入 Harness → 记忆 → 扩展性

我们的排期在此基础上做了一处调整：**把本地工作区（M3）放在 Skill 体系（M4）之前**。原因是 Skill 的渐进式披露依赖 `read_file` 读取本地 Skill 目录 —— 没有工作区，Skill 就只能退回 localStorage 的老路。

## 2. 里程碑总览

| 里程碑 | 主题 | 层 | 工期 | 前置 |
|---|---|---|---|---|
| [M1](phases/M1-agent-runtime.md) | AI 交互引擎与工具系统 | L1 + L2 | 4–5 周 | — |
| [M2](phases/M2-harness.md) | Harness 安全与控制平面 | L3 | 2–3 周 | M1 |
| [M3](phases/M3-local-workspace.md) | 本地工作区与记忆 | L5 + 能力层 | 3–4 周 | M1 |
| [M3.5](phases/M3.5-unified-workspace-ui.md) | 统一工作台与交付物模型 | UI + L5 | 2–3 周 | M3 |
| [M4](phases/M4-skill-system.md) | Skill 体系 | L4 | 2–3 周 | M2, M3 |
| [M5](phases/M5-pptd-engine.md) | PPTD 演示文稿引擎 | 应用 | 5–7 周 | M4 |
| [M6](phases/M6-multi-agent.md) | 多 Agent 协作 | L1 扩展 | 4–5 周 | M2 |

## 3. 依赖关系

```
        M1 交互引擎 + 工具系统  (4-5w)
              │
      ┌───────┴───────┐
      ▼               ▼
  M2 Harness      M3 本地工作区
    (2-3w)          (3-4w)          ← 可并行：M2 前端，M3 主要 Rust
      └───────┬───────┘
              ▼
      M3.5 统一工作台 (2-3w)         ← 收敛 artifact 与文件为同一模型
              │
              ▼
        M4 Skill 体系 (2-3w)
              │
      ┌───────┴───────┐
      ▼               ▼
  M5 PPTD 引擎    M6 多 Agent
    (5-7w)          (4-5w)          ← 可并行
```

M3.5 是 M3 复盘后插入的收敛阶段，不是新增范围。放在 M4 之前的原因：M4 的 Skill 目录与 M5 的 PPTD 产出都会需要「在文件树里可见、可预览、可版本化」，若不先统一交付物模型，两者会各自再长一套查看器。

## 5. 每个里程碑的「可演示成果」

排期不看代码量，看能不能演示。每个里程碑必须有一个能当着人跑的 demo：

| | Demo |
|---|---|
| **M1** | 输入「看看当前目录有什么文件，把最大的那个读出来总结」，AI 连续调用 `list_dir` → `read_file` → 输出总结，过程逐步显示，中途可点停止 |
| **M2** | 同样的任务改成写文件，弹出确认框，点「拒绝」后 AI 说明原因并换方案；侧栏能看到完整运行账本 |
| **M3** | 新建项目选一个本地文件夹，文件树显示内容；在 Finder 里新增一个文件，树自动刷新；AI 能读到它 |
| **M3.5** | 交办「写一份需求规格」，右栏逐字长出文档，写完后文件树与 Finder 里立刻出现该文件；再改一版能切版本、看 diff、一键回滚 |
| **M4** | 装一个 Skill（拖入目录），命令面板出现，唤起后 AI 主动读取该 Skill 的 reference 再干活 |
| **M5** | 交办「基于这份文档做一版汇报 PPT」，产出可直接给客户的 pptx |
| **M6** | 交办一个复合任务，看到主 Agent 拆解并派发给 2–3 个子 Agent 并行执行 |

## 7. 风险与应对

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| M1 工具调用在部分模型上不稳定（尤其国产模型） | 高 | M1 延期 | M1 内置能力探测，不支持的模型自动降级为纯对话；优先用 Claude/GPT 打通，再逐个适配 |
| Rust 侧从零开始，团队不熟 | 中 | M3 延期 | M3 前预留 3pd 学习；优先用现成 crate（notify / rusqlite / ignore）不自己造 |
| 上下文与 token 成本失控 | 中 | 成本 | M1 就加每轮 token 上限与统计；大结果句柄化不可延后 |
| PPTD 渲染保真度不达预期 | 中 | M5 返工 | M5 拆成「预览优先」两段交付，先 HTML 保真再攻导出 |
| 长任务因关窗中断 | 中 | 体验 | M1 做会话快照；接受首版限制，见 [M6 后评估](05-post-m6-evaluation.md) |
| 范围蔓延 | 高 | 全线延期 | [00-vision-and-scope.md §5](00-vision-and-scope.md) 的非目标清单是硬约束，新需求先对照 |

## 8. 阶段性检查点

每个里程碑结束时回答三个问题，答不上来就不算完成：

1. 第 5 节的 Demo 能当着人跑通吗？
2. 这个里程碑引入的能力，在特性开关关闭时主干是否完全不受影响？
3. 下一个里程碑的前置条件是否真的满足了（不是「大致差不多」）？
