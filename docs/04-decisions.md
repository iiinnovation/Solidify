<a id="adr-0001"></a>
## ADR-0001：数据主场在本地，Supabase 降为同步层

- **状态**：接受
- **日期**：2026-08-11

### 决定

项目的真相源是本地文件系统。一个项目 = 一个用户可见的本地目录。Supabase 保留，但职责收窄为账号、跨设备同步、团队共享快照和可选的托管模型代理。应用在完全没有 Supabase 的情况下必须能完整运行。

### 原因

- 四根支柱中的「文件管理」和「项目作业区」在云端虚拟目录上做不出该有的体验
- Agent 要真正干活就必须读写用户的真实文件，而用户的文件在本地
- 本地目录可以用 Finder 打开、拖拽、备份、进网盘、进 Git —— 这是相对 SaaS 最直接的信任来源和体验优势
- 大文件（原始材料、素材、导出物）上云的带宽与存储成本不划算

### 代价

- Rust/Tauri 层要从 31 行长到 1.5k–2k 行
- 需要处理本地文件移动、重命名、丢失后的引用失效
- 需要一次性迁移路径，把老的云端项目导出到本地工作区
- 团队协作能力受限，协作粒度只能是「文件/版本」而非实时

### 迁移原则

- 新建项目直接本地优先
- 老项目提供一次性导出，**不做长期双向同步**（双向同步是本地/云端双真相的根源）
- Supabase 表结构基本保留，语义从「主库」变为「快照与共享」

<a id="adr-0002"></a>
## ADR-0002：Agent 循环实现在前端 TypeScript

- **状态**：接受
- **日期**：2026-08-11

### 决定

L1 查询引擎与 L2 工具调度用 TypeScript 实现，运行在前端渲染进程。Rust 侧只提供工具执行所需的原语（文件、进程、数据库），不参与循环调度。

### 备选方案

| 方案 | 否决原因 |
|---|---|
| 循环放 Rust | 现有 18KB 的 SSE 解析与流式状态同步（`use-chat.ts:249-410`）全部要重写；Rust 侧异步生成器与 UI 事件流的对接成本高 |
| 循环放 Edge Function | 与 ADR-0001 本地优先直接冲突：Agent 要读写本地文件，循环在云端就必须把文件内容来回传 |
| 起一个本地 Python 边车跑成熟框架 | 要给每台机器分发 Python 运行时与原生依赖；跨语言的权限上下文与中断语义难以保持一致 |

### 原因

- `use-chat.ts` 已有的流式解析、增量 artifact 跟踪、React 状态同步是可复用的资产，agent loop 本质是在它外面套一层循环
- 异步生成器 + 背压的模式（参考架构第一条工程原则）在 TS 里表达最自然，且消费端就是 UI
- 权限的 `ask` 状态需要循环真正挂起等待用户输入 —— 循环与 UI 同进程时语义最直接
- 语言栈单一，团队认知负担最低

### 代价与已知限制

- **关闭窗口 = 循环中断**。M1 通过会话快照做到「可恢复」，但不是「后台继续跑」
- 大量工具结果在渲染进程内存中流转，需要句柄化机制控制内存

### 重新评估条件

出现以下任一情况时，重新评估把 L1 下沉 Rust：

- 用户明确需要「关窗后任务继续跑」
- 单次运行的工具调用超过 50 轮成为常态
- 渲染进程内存占用因工具结果成为瓶颈

<a id="adr-0003"></a>
## ADR-0003：PPT 能力自研，不依赖任何在线渲染服务

- **状态**：接受
- **日期**：2026-08-11

### 决定

采纳 PPTD 格式规范（YAML 中间 DSL）与其配套的设计方法论作为**知识资产**，自行实现解析器、渲染器和导出器。不接入任何依赖外部在线编辑器的渲染或导出链路。

首版明确**不支持动画**；高级图表类型降级为图片嵌入；自定义几何路径降级为基础形状。

### 背景

调研的开源方案 `open-kimi-ppt-skill` 有两部分：

| 部分 | 评价 |
|---|---|
| PPTD 格式规范（2029 行）、SKILL 方法论、示例工程 | 高价值，直接采纳 |
| 本地编辑器 `editor/`、导出脚本 `export_pptx.py` | 不可用 |

关键事实：该项目**本地没有任何渲染器**。`editor/app.js:11-12` 与 `export_host.html` 都是把 `https://www.kimi.com` 嵌入 iframe，通过 penpal 做 postMessage RPC；导出流程是起本地 http server → 全局安装 `agent-browser`（Chromium 自动化）→ 在 iframe 里由远端 SDK 生成 pptx。

### 原因

- 渲染与导出能力完全依赖第三方在线服务，服务变更即失效，不可作为产品核心能力
- 运行期依赖链过长：Node 18+ / npm / python3 / PyYAML / Chromium / agent-browser / 公网访问
- 逆向性质的调用方式在商业产品中存在合规风险
- Solidify 已有 `pptxgenjs` 依赖和 `slide-export.ts` 的导出经验，自研有基础

### 采纳的与放弃的

**采纳**：PPTD 的 `.pptd` 清单 + `pages/*.page` + `media/` 结构；960×540pt 绝对坐标系；元素模型（text/shape/line/image/icon/table/chart）；主题变量（`$accent` 形式）；SKILL.md 的 PPT 生产工作流。

**放弃**：`editor/`、`export_pptx.py`、`export_images.py`、agent-browser 依赖、动画规范（保留在文档中作为未来选项）。

### 代价

- MVP 约 5–7 人周，完整覆盖 12–16 人周
- 首版保真度低于 Kimi 官方渲染
- 动画能力缺失（预览可用 CSS 模拟，导出丢弃）

### 关键配套要求

PPTD 是绝对定位格式，模型直接计算坐标必然出现元素重叠与出血。**必须配套视觉自检回环**：渲染 → 截图 → 多模态模型审阅 → 修正 YAML → 重渲染。这依赖 M1 的 `capture_preview` 工具，是 M5 排在 M1 之后的硬原因。

<a id="adr-0004"></a>
## ADR-0004：Skill 采用目录 + SKILL.md 格式

- **状态**：接受
- **日期**：2026-08-11

### 决定

Skill 从「一个 systemPrompt 字符串」升级为一个目录：

```
skill-name/
├── SKILL.md          frontmatter（name/description/version/allowed-tools）+ 工作流正文
├── reference/        按需加载的详细规范
├── examples/         少样本示例
└── assets/           模板与静态资源
```

存储位置从 localStorage 迁移到文件系统（用户级目录 + 工作区级目录）。采用与主流 Agent 工具一致的 frontmatter 约定，不自创格式。

### 原因

- 现有形态（`src/lib/skills.ts` 21KB 全是 prompt 字符串 + `skill-store.ts` 存 localStorage）没有资源、没有工具绑定、没有版本，清缓存即丢失
- **渐进式披露**是核心：一份 2000 行的格式规范不可能塞进 system prompt，只能让模型按需读取。这要求 Skill 的内容以文件形式存在，且模型有 `read_file` 能力
- 采用通用约定让 Skill 可以在生态间流通，用户可以直接拿现成的 Skill 用

### 代价

- 依赖 M3 的本地工作区能力，无法提前做
- 需要把现有 10 个内置 Skill 全部迁移
- Web 端无文件系统，需要设计降级方案（内置 Skill 打包进 bundle，自定义 Skill 不可用）

### 安全约束

Skill 内的可执行部分（如有）**不能是任意脚本执行**。必须走 L2 已注册的工具，`allowed-tools` 声明白名单，并受 L3 权限策略约束。

<a id="adr-0005"></a>
## ADR-0005：工具执行下沉 Rust，调度留在 TS

- **状态**：接受
- **日期**：2026-08-11

### 决定

工具的**调度、校验、权限判定**在 TS（L2 + L3）；工具的**实际执行**中涉及文件系统、进程、数据库的部分下沉到 Rust command。

路径沙箱校验（`resolve_in_workspace`）**必须在 Rust 侧实现**，TS 侧的校验只作为提前失败的优化，不作为安全边界。

### 原因

- TS 侧的任何校验在渲染进程内都可能被绕过，安全边界必须在特权侧
- 文件遍历、监听、SQLite 在 Rust 生态有成熟 crate（`ignore` / `notify` / `rusqlite`），性能与正确性都优于 JS 实现
- 保持 ADR-0002 的调度单一语言，同时不牺牲安全

### 代价

- 每个涉及本地资源的工具都要跨 IPC，有序列化开销
- Web 端这些工具不可用，需要在注册表中按运行环境过滤

### 强制测试要求

沙箱校验必须覆盖：`../` 穿越、符号链接逃逸、绝对路径注入、Windows UNC 路径、大小写不敏感文件系统上的路径混淆。缺少任一用例不允许合并。

<a id="adr-0006"></a>
## ADR-0006：本地索引用 SQLite

- **状态**：接受
- **日期**：2026-08-11

### 决定

每个项目工作区内维护一个 `.solidify/index.db`（SQLite），存放文件索引、全文检索、向量、会话快照与运行账本。

### 原因

- 单文件、零运维、可随项目目录一起拷贝备份
- FTS5 提供全文检索，`sqlite-vec` 扩展提供向量检索，一个文件覆盖两种检索
- 与 ADR-0001 的「项目自包含」一致：索引跟着目录走

### 已知问题

⚠️ **FTS5 默认分词器不切中文**。首版使用 `trigram` 分词模式（SQLite 3.34+ 内置，无需额外扩展），检索质量可接受。若后续质量不足，再评估引入 ICU 分词器或 jieba 预分词。

⚠️ 索引是**派生数据**，必须可以随时删除重建。任何真相不得只存在于 `index.db` 中。

<a id="adr-0007"></a>
## ADR-0007：运行账本与聊天记录分离

- **状态**：接受
- **日期**：2026-08-11

### 决定

Agent 的执行过程记录在独立的**追加式事件账本**中，与聊天消息流分离。聊天消息不是唯一真相来源。

事件类型至少包括：

```
run.started / run.completed / run.failed
tool.requested / tool.progress / tool.completed / tool.failed
permission.required / permission.resolved
artifact.created / artifact.updated
model.called
```

### 原因

- 聊天消息是给人看的叙述，账本是给回溯、调试、计费、审计用的结构化事实，两者的读者和生命周期都不同
- Tombstoning 机制要求「UI 可以隐藏某条消息，但事实必须留存」—— 只有分离才能做到
- 成本分析、失败复盘、性能优化都需要结构化事件，从聊天文本里反推不可行

### 代价

- 双写成本
- 账本会快速增长，需要按运行归档与保留策略

### 约束

账本只追加，不修改、不删除单条。清理以「整个运行」为单位归档。

<a id="adr-0008"></a>
## ADR-0008：运行事件采用同源词汇、实时与持久分层

- **状态**：接受
- **日期**：2026-08-13
- **补充**：[ADR-0007](#adr-0007)

### 背景

ADR-0007 决定将运行账本与聊天记录分离，但未区分 UI 控制事件与可回放审计事实。M2 引入审批挂起后，事件可能携带 `AbortSignal`、Promise resolver 或瞬时进度；这些值既不能安全序列化，也不应成为恢复真相源。

### 决定

运行时与账本共享同一套领域命名和稳定 ID，但使用两个明确投影：

- **实时控制事件**：供 UI 与运行协调使用，可以高频、可丢弃、不可回放，例如 `message.delta`、`tool.progress`、`permission.required`。
- **持久事实事件**：只含无损 JSON，可追加、可回放，例如 `run.started`、`tool.requested`、`approval.asked`、`approval.decided`、`tool.completed`、终态事件。

实时事件不得直接写入账本。账本写入器从同一运行边界产生持久事实，而不是维护另一套业务状态机。两种投影通过 `runId`、`callId`、`requestId` 关联。

审批必须先追加 `approval.asked`，得到结果后追加且仅追加一个匹配的 `approval.decided`；如果决定无法落账，不得返回未审计的允许。进度可聚合为工具结果的耗时和摘要，但不逐帧持久化。

### 原因

- resolver、signal 和流式增量不是持久数据，强行序列化会制造无法恢复的假状态。
- UI 需要低延迟高频事件，审计需要低噪声、稳定、可回放的事实，两者保留策略不同。
- 共享领域 ID 与命名仍避免两套互相漂移的业务模型。

### 约束

- 所有持久事件必须是无损 JSON 快照，写入后视为不可变。
- 模型实际看到的消息、工具结果和权限拒绝必须能从持久事实重建。
- 遥测从持久账本派生；导出前可脱敏，但不得改写权威账本。
- 缺少审批应答者、应答者异常、非法结果或审计写入失败时一律 fail-closed。
