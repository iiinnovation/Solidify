# Draw.io 大附件输出耗尽恢复修复

日期：2026-09-10。对应用户提供的 `conv-1789022394703-2` 运行台账，遵循 [分阶段运行时方案](agent-runtime-staged-workflow-refactor-proposal.md) 的有界恢复规则，不更换模型或强制禁用思考。

## 已确认的问题

首轮使用 `deepseek-flash`、输出上限 8192，最终 `textLength=0`、`toolCallCount=0`、`stopReason=max_tokens`，但存在 reasoning 输出。`reasoningLength` 是 JavaScript 文本长度计数，不是 token 数；费用和输出预算以 Provider 的 usage 为准。该轮尚未形成可供 Draw.io 渲染的正文，不能据此诊断为绘图渲染失败。

旧恢复策略只收紧工具结果和工作区检索插槽，没有处理用户消息中的 `<attachments_inline>`。这份附件仍在 128K 上下文窗口以内，因此通用历史裁剪也不会触发。结果是第二次请求保持 24,378 个附件 token 估算值和 8192 输出上限，只增加了恢复提示词；“输入已自动精简”的提示不符合实际。

`tools=[]`、`toolChoice=none` 是 Draw.io 生成阶段的正常能力隔离，温度由 0.7 收敛到 0.2 也是既有阶段策略。没有把它们改成重新检索或开放写文件。`deepseek-flash` 的默认输出上限来自现有 DeepSeek 名称匹配，本轮没有未经网关能力确认就增加额度或添加模型专属思考参数。

## 修复行为

上下文编译器在 `compact_recovery` 时增加独立的 inline 附件预算，按模型窗口和输出预留计算，范围为 512 至 6000 个估算 token。该预算覆盖所有已匹配附件条目及恢复说明，不包含外层 envelope 和用户问题。后续通用上下文预算仍继续执行。

只替换与运行时 `AttachmentResource` 所生成完整条目完全一致的文本，不把用户任意输入的类 XML 文本解析为授权附件。保留条目之外的问题、补充要求，以及图片、工具协议块和 assistant 消息；不改原始附件或存储的历史。重复全文仅在最新出现位置保留摘录，旧重复项省略。

超预算内容替换为带来源 ID/文件名及 `truncated=true` 的 `attachment_excerpt`。识别 Markdown 标题及“一、”“2.1”等编号标题，在各章节间分配预算，优先保留标题，正文使用已有的首/中/尾采样。元数据都无法放入预算的条目会被省略并计入 `omittedSources`；恢复说明明确指出内容不完整，不得把省略理解为不存在，也不得补造关系。这是有损恢复，不是全文语义摘要或完整性保证。

同一 staged-delivery 运行的后续格式修复和正文续写继续使用恢复输入，避免重新带回大附件。普通开放式 Agent 在恢复后获得新的工具结果时恢复原有正常证据预算。恢复机会仍至多一次，续写、格式修复和总运行预算上限不变。没有增加模型调用来总结附件，也不读取或保存 reasoning 原文。

系统提示不再无条件声称“输入已经精简”；工具为空时不再建议调用“下一工具”。`model.called.contextStats` 新增 `inputMode` 与 `inlineRecovery`，后者包含预算、条目精简前后 token 估算、匹配数、改变数、重复省略数和整项省略数。未匹配或无需裁减时改变数为 0，不能仅凭 `compact_recovery` 标签认定请求已缩小。

同时修复了通用采样器的 `slice(-0)` 边界：尾部配额为零时不得把整段原文重新拼回，否则可能突破预算。
