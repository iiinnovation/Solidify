## 1. 背景：三处偏离

| 文档写的 | M3 结束时的实现 | 代码位置 |
|---|---|---|
| UI 层「三栏工作台」 | 两栏：ChatPanel(360–520px) + ArtifactPanel | `src/routes/chat.tsx:11` |
| 支柱二「项目 = 作业上下文」 | 项目是一个要**导航过去**的独立页面 | `src/routes/workspace.tsx` |
| 支柱二「项目内聚合交付物版本」 | Artifact 存在 chat-store/localStorage，与文件树无关 | `src/stores/chat-store.ts` |

第三条最要命：Agent 正在 `write_file` 写 `03-交付物/需求规格.md`，用户要看这个文件必须离开对话页；而模型用 `<solidify-artifact>` 产出的同一份东西，又根本不在文件系统里。**同一个交付物有两种存在形式、两个查看器、两套导出路径。**

`ArtifactPanel` 与 `FilePreview` 是这一分裂的直接症状。

## 2. 目标

把「交付物」收敛成**项目目录里的一个文件**，并让三栏工作台成为唯一的工作界面。

一句话：**文件树里看得见的，就是 AI 产出的；AI 产出的，就是文件树里看得见的。**

## 3. Demo（验收标准）

> 打开一个本地项目，左栏是文件树。交办「基于 01-输入材料 里的访谈记录写一份需求规格」。
>
> 右栏实时逐字长出文档；写完后**文件树里立刻出现 `03-交付物/需求规格.md`**，Finder 里也能看到这个文件。
>
> 再让 AI 改一版。右栏能切回上一版、看 diff、一键回滚。
>
> 全程不需要离开这一个界面。

## 4. 设计决定

以下五条在动手前已定，实现时不得擅自偏离；要改走 [04-decisions.md](../04-decisions.md) 追加 ADR。

### D1 · 列顺序：文件 · 对话 · 渲染

```
┌────────────────────────────────────────────────┐
│ Header · 项目名 ▾            阶段：方案 ▾       │
├─────────┬──────────────┬───────────────────────┤
│ 项目文件 │  对话         │  渲染 / 预览          │
│ ▾01-输入 │ ┌──────────┐ │  ┌─────────────────┐ │
│  ·访谈.md│ │用户: 写需 │ │  │ # 需求规格       │ │
│ ▾02-过程 │ │求规格     │ │  │                 │ │
│ ▾03-交付 │ ├──────────┤ │  │ ## 1. 背景       │ │
│  ·需求规格│ │AI ▸ write │ │  │ ...             │ │
│         │ │_file ✓    │ │  │                 │ │
│ ─────── │ └──────────┘ │  └─────────────────┘ │
│ 对话(3)  │ [输入框    ] │                       │
└─────────┴──────────────┴───────────────────────┘
  260px       400px            flex (最大)
```

渲染区保持最大面积——现状 chat 已经是窄栏（`chat.tsx:17` `minLeft:360 / maxLeft:520`），说明产品重心本来就在产出物上。左栏承接**现有 Sidebar 槽位**，`MainLayout` 结构不变。

### D2 · Artifact 就是文件

```
Document ≡ 项目里的一个文件
  path      03-交付物/需求规格.md          ← 唯一标识，取代 activeArtifactId
  renderer  由扩展名 + 可选 type 推导        ← 复用现有渲染器族，不重写
  versions  .solidify/artifacts/<safe(path)>/v{n}{ext}
```

全局 artifact 表消失，降级为消息上的引用 `{path, messageId, version}`。文件树、查看器、导出、检索从此指向同一个对象。

`.solidify/artifacts/` 槽位在 M3 已预留（`src/lib/workspace/scaffold.ts:8`），不需要改工作区格式。

### D3 · 保留 `<solidify-artifact>` 通路，完成后自动落盘

现有两条产出通路必须收敛，但**不能牺牲流式预览**：

| 通路 | 机制 | 流式 | 是真文件 |
|---|---|---|---|
| A | 正文里的 `<solidify-artifact>` 标签，`use-chat.ts:54` 增量解析 | ✅ | ❌ |
| B | `write_file` 工具，原子写入 | ❌ | ✅ |

取 A 的流式 + B 的落盘：

```
模型流式吐 <solidify-artifact title="需求规格" path="03-交付物/需求规格.md">
   ↓ 边解析边渲染（内存缓冲，右栏实时可见）
闭合标签出现 → 物化
   ↓ 旧内容快照到 .solidify/artifacts/    ← 写入前
   ↓ 写盘 → watcher 感知 → 文件树刷新 → activePath 指向它
```

`write_file` 继续负责其他文件操作，两者最终都是文件。

**不选「只保留 write_file」**：会丢掉流式预览，且 `toolCalling` 关闭或模型不支持工具时完全产不出交付物——M1-29 已记录 Claude 中转与 DeepSeek 的工具调用稳定性问题，不能把交付物能力单点押在工具调用上。

`path` 属性需要新增进 system prompt。模型不给时按 `03-交付物/{sanitize(title)}.{ext}` 派生兜底，`type→ext` 映射：`document→md`、`code→按语言`、`mermaid→mmd`、`chart→json`、`drawio→drawio`、`slides→md`。

### D4 · 写入前快照

每次 AI 写入**已存在**的文件前，先把当前磁盘内容快照到 `.solidify/artifacts/<safe(path)>/v{n}{ext}`，附 `meta.json` 记录 `{n, ts, runId, messageId}`，保留最近 20 版后淘汰最旧。

选**写入前**而非写入后：用户可能在 VSCode/Finder 里手工改过文件，写入前快照能把这些改动一并保住；写入后快照只记录 AI 的状态，用户的手工编辑会被静默吃掉。这直接服务于「用户没有应内回退手段」这个要解决的问题。

新建文件没有可保护的旧内容，不产生 v1；版本链 = `[v1…vn] + 磁盘当前内容`。

### D5 · 物化走权限门，但新建放行 ⚠️ 建议默认值，实现前复核

物化是一次真实写盘，走**与 `write_file` 相同**的 PolicyEngine 路径。默认策略：

| 场景 | 判定 | 理由 |
|---|---|---|
| 在 `03-交付物/` 下**新建**文件 | `allow` | 无损；且用户刚刚明确要求产出这份交付物 |
| **覆盖**任何已有文件 | `ask` | 有损，且 D4 的快照也在这一步 |
| 其他目录 | 沿用现有默认策略 | — |

若一律 `ask`，用户每产出一份交付物都要确认一次，很快会疲劳到无脑点允许——这正是 [M2 风险表](M2-harness.md) 列明要避免的失败模式。

> 本条是建议默认值，不是已锁定决定。开工前需与产品复核；若改判，只影响 `policy.ts` 的默认表，不影响其余设计。

## 6. 里程碑内的顺序建议

```
第 1 周   A（数据模型）—— 做完就能在 Finder 里看到 AI 产出的文件
第 2 周   B（三栏布局）
第 3 周   C（版本 UI）+ D（降级与测试）+ 缓冲
```

A 与 B 之间是硬依赖：`DocumentViewer` 需要 D2 的统一模型才有东西可渲染。C 可与 B 并行（不同人）。

## 7. 风险

| 风险 | 概率 | 应对 |
|---|---|---|
| 外部编辑冲突：用户在 VSCode 改了文件，AI 同时覆写 | 高 | M3.5-13 必做。watcher 已能感知变更，落盘前比对 mtime，不一致则弹确认。这条不做就破坏了支柱一「不劫持文件」的承诺 |
| 模型不遵守 `path` 属性 | 中 | D3 的派生兜底路径必须先于 prompt 调整实现，不能依赖模型合作 |
| 900px 最小窗口放不下三栏 | 中 | M3.5-09 的图标条降级；验收必须覆盖 900×600 与 1280×900 两档 |
| 存量 artifact 迁移丢数据 | 低 | 只导出不删除，与 M3-15 同策略；迁移失败保留内存态只读可见 |
| 每份交付物一次确认框导致审批疲劳 | 中 | D5 的新建放行；若产品否决该默认值，需另设批量授权机制 |
