## 0. 设计结论与实施边界

执行面位于工具边界以下，复用已有任务、计划、权限与批次检查点，不另建一套任务事实源。

| 需求 | 复用机制 | 仍需补充 |
|---|---|---|
| 谁能调用 | CapabilityLease、任务阶段工具名单、工具注册与筛选 | 转换工具的注册与 batch 阶段授权；Shell 的显式默认拒绝 |
| 用户授权 | PolicyEngine、approval channel | 平台能力检查、进程工具白名单及授权范围 |
| 文件范围 | FolderTask inventory、计划、batchToken | 外部转换文件的纳入规则与旧任务重新入队 |
| 输入一致性 | 大小、mtime、SHA-256、路径校验 | 按调用暂存经过校验的输入 |
| 执行隔离 | 新增 Rust SandboxProvider | 平台探测、依赖范围、资源限制与隔离测试 |
| 暂停和取消 | 现有任务状态、run 中断 | Rust 活动执行登记、取消通道和进程回收 |
| 大输出 | handleizeLargeResult、read_handle | 转换结果大小限制、句柄可见性与失效恢复 |
| 完成与交付 | update_folder_task_batch、结果校验和确定性输出 | 转换来源记录、错误分类与端到端测试 |

新增工作不止一个 Rust 模块和一个工具：还包括扫描/计划/入队规则、前后端能力投影、进程管理、结果来源、依赖交付和产品状态反馈。

本文中的接口、状态处理和默认预算均为拟实现规格。示例不代表已通过平台隔离验收。

## 1. 范围与首版交付

### 1.1 当前代码事实

当前 read_folder_task_file 在内置解析失败或不支持时返回工具错误，并不返回 awaiting_external_parser 作为统一兜底信号。新建任务会把不支持格式的技术决策默认解析为 skip；批次领取只选择 pending 文件。因此，“等文件进入 awaiting_external_parser，再调用转换器”无法直接接入现有流程。

主要核对位置：

- src/lib/tools/builtin/folder-tasks.ts：读取工具与批次更新工具。
- src/stores/folder-task-store.ts：resolveTechnicalDecisions。
- src-tauri/src/fs/folder_tasks.rs：扫描、计划范围、claim_folder_task_batch_impl。
- src/lib/engine/loop-runtime.ts：FOLDER_TASK_STAGE_TOOLS、restrictFolderTaskCapabilityLease。
- src/lib/tools/registry.ts、src/lib/engine/chat-context.ts：工具注册与任务专用工具范围。

### 1.2 两个阶段

| | Phase A：extract_document_text | Phase B：run_shell |
|---|---|---|
| 目标 | 补齐图片与扫描 PDF 的文本读取 | 模型编写命令，执行更灵活的文件处理 |
| 命令来源 | Rust 固定的转换流程 | 模型生成命令 |
| 模型输入 | batchToken、relativePath、method 枚举 | 命令及受限工作环境参数，另行定义 |
| 默认 | 环境就绪且文件已纳入计划时可用 | 关闭，需开关、显式能力授权与确认 |
| 交付 | 文本、页级来源、解析告警 | 命令结果与可审核的产物导入 |
| 首版范围 | macOS、PNG/JPEG 图片、扫描 PDF | 不在 Phase A 内实施 |

已有内置解析器继续负责其支持的文本和文档格式。首版不承诺旧版 Office、压缩包、任意脚本或任意文件修改；这些不得提前写进工具描述和产品能力列表。

Shell 对跨文件计算、转换和生成可能有价值。Phase A 只验证受限转换执行，不代表已经解决 Phase B 的命令权限、依赖环境、产物交付和完整进程树管理。

### 1.3 Phase A 的用户体验

- 新任务展示“可直接读取”“可通过 OCR 读取”“当前无法读取”的数量及原因。
- 仅支持图片/OCR 的输入也应能创建、制定计划和启动，不能继续只以 inventory.readableFiles > 0 判断是否可启动。
- 缺少转换组件时展示安装/启用入口和受影响文件，不把依赖缺失包装成业务问题。
- 正在转换时展示当前文件与页进度；暂停显示为“正在停止”，进程退出后再确认已暂停。
- 扫描文本不可靠、页数超限或部分页面失败时明确标注，不能把不完整结果展示为完整读取。
- 最终仍由模型按已确认 RecipePlan 处理文本，经结果校验和检查点提交后进入结果审阅/完成流程。

## 2. 不变量

1. 沙箱保护宿主访问边界，不证明模型结论正确。结果结构校验只校验契约；语义准确性仍需证据和结果审阅。
2. Phase A 禁止网络，工具入参不可改变这一策略。Phase B 若需要联网，另行定义授权和持续可见的网络状态。
3. 用户源文件只读，转换进程只写调用专属临时目录；应用私有数据、.solidify 和 .git 不对执行环境开放写入。
4. 批次租约是数据访问授权，不是进程句柄。暂停、取消、到期必须由执行管理器主动停止活动进程。
5. 临时目录不是恢复事实源。恢复依赖任务数据库和已保存的检查点，不依赖进程、临时路径或仅存在于内存的句柄。
6. 转换成功不等于文件处理完成。只有 update_folder_task_batch 可以提交批次处理结果，Shell 也不能直接修改检查点。
7. 每次返回有效转换结果前，再次校验任务状态、租约和输入来源。停止后晚到的结果不可被接受。
8. 隔离能力或必需依赖不可用时明确禁用对应方法，不退化为宿主裸进程执行。

## 3. 文件状态与解析结果

### 3.1 扫描、计划与入队

新增“解析路由”元数据（名称待实现时定稿）：native、external、unavailable，另记录可用方法与缺失依赖。这是文件处理能力，不能与 item.status 混为一谈。扫描无需先做完整 OCR；PDF 可在读取阶段识别是否需要 OCR。

计划预览必须纳入“内置可读 + 可外部转换”的已选文件，展示 OCR 范围与预算。inventory、计划计数、扩展名筛选、任务入口、推荐启动和对话摘要应使用一致口径。

| 触发条件 | 状态/结果 | 后续动作 |
|---|---|---|
| 已选文件可内置解析或可外部转换，且已纳入计划 | pending | 可被 claim 领取 |
| claim 成功 | processing | 绑定唯一活动批次 |
| 内置读取成功 | processing + parsed | 模型处理并提交检查点 |
| 内置读取识别为需要 OCR | processing + needs_external_parser | 在同一租约下调用转换器 |
| 转换成功且内容通过完整性检查 | processing + parsed | 模型处理并提交检查点 |
| 转换器缺失/不可用 | 检查点后 awaiting_external_parser | 安装/启用后显式重试；不得无界自动循环 |
| 无可用读取方法且用户接受跳过 | 检查点后 skipped | 保留原因和清单 |
| 损坏文件、转换超时或转换失败 | 检查点后 failed | 展示具体错误，允许重试/跳过 |
| 模型结果保存成功 | completed | 纳入结果与输出 |
| 暂停、取消、租约失效 | 停止进程，未提交项回 pending | 按任务状态决定是否允许再次领取 |

needs_external_parser 是拟新增的结构化读取结果，不是新的数据库 item 状态。awaiting_external_parser 是脱离活动处理后的等待状态；处于该状态的文件不能绕过 claim 直接交给转换器。

实现时需扩展 checkpoint 的前端 schema、状态规范化、Rust 校验和进度统计，使依赖缺失可以提交为 awaiting_external_parser。一次完整 checkpoint 仍需交代整个活动批次，不能先把某个 processing 项私自出队。

解析结果至少包含：status、可用方法、reasonCode、warnings、页数/截断信息、parser 与版本、sourceHash。未知错误不能一律标成“需要 OCR”；密码保护、路径越界和快照失配分别报告。

### 3.2 旧任务和依赖变化

- 旧任务中 skipped 或 awaiting_external_parser 的文件不会因安装了 OCR 组件就被自动扩入执行范围。
- 若文件仍属于已确认计划、快照未变化，可通过用户重试动作回 pending；Rust 必须验证范围和当前能力。
- 若原计划已排除该格式，需重新生成范围预览并确认，或明确引导创建新任务。重新入队不能绕过计划授权。
- 输入内容已变化时，撤销过期预览并走重新扫描/确认流程，不能用旧快照静默接受新内容。
- 安装/移除组件后刷新能力清单；已创建任务保留历史处理与错误记录。

## 4. 控制面与执行面

~~~text
模型 → extract_document_text
    → 工具注册/阶段名单 → PolicyEngine → Tauri IPC
    → Rust 校验任务、批次与文件范围
    → 按调用暂存和验证输入
    → ExecutionManager 登记活动执行
    → SandboxProvider 启动并监督固定转换流程
    → 再校验租约、结果完整性与来源
    → 有界文本/结果句柄 → 模型
    → update_folder_task_batch → 确定性输出
~~~

调用身份沿用 taskId、runId、batchToken。Rust 另生成 executionId，只用于关联进程、取消和日志，不授予额外文件访问权。文件路径集合从数据库推导，不接受模型传入任意只读目录。

Phase A 同一批次最多一个活动转换。前端 concurrencySafe: false 只约束单次工具调度，Rust 还需防止多个 IPC 调用、重试或旧 run 造成并发执行。

## 5. Rust 执行模块

建议新增 src-tauri/src/fs/sandbox_exec.rs，并将平台实现、输入暂存与执行管理拆成内部模块。现有 sandbox.rs 继续负责路径边界；不能把路径校验等同于进程隔离。

### 5.1 策略与结果契约

| 结构 | 核心字段 |
|---|---|
| SandboxPolicy | stagedInputPaths、workDir、runtimeReadPaths、allowedBinaries、network、limits |
| ExecutionIdentity | taskId、runId、batchId、executionId；租约 token 仅内部使用 |
| ExecutionControl | 取消信号、租约截止时间、活动进程/监督句柄 |
| SandboxOutcome | 状态、退出码、耗时、输出字节数、错误分类、受限 stderr |
| ExtractedDocument | 文本或页级结果、sourceHash、parserVersion、语言包版本、页数、warnings、完整性标记 |

策略由 Rust 从可信任务状态和安装组件清单构建。模型不能设置宿主路径、执行器路径、环境变量、资源上限或网络开关。

输出达到硬上限时终止执行并返回明确错误；若产品允许部分页结果，必须标记不完整并在模型提示及最终结果中保留，不能截断后仍标为完整成功。

### 5.2 Provider 与能力探测

SandboxProvider 提供 probe、start/run、terminate、wait/reap 的等价能力。具体接口可以异步实现，但必须允许监督任务在转换进行中处理取消，不能以一个不可中断的同步 run 函数封住整个生命周期。

ExecutionManager 存在于 Tauri State，维护活动执行的内存登记，不另建持久化 session 表。每项登记包含进程控制句柄、目录所有权、任务身份、截止时间及状态。

probe 返回按方法区分的能力及原因：

- 隔离器能否启动、目标平台/架构是否受支持。
- 固定二进制、动态库、PDF 渲染器、OCR 语言包是否齐全，版本和完整性是否符合安装清单。
- 必需的读写/网络隔离及进程终止能力是否通过最小自检。
- 本机实际可执行的资源限制，以及未提供的限制。

启动时探测，组件变更后重新探测；调用前 Rust 再检查。前端 registry 与 policy 消费能力投影。tauri-only 只表示运行在桌面端，不能代替 macOS/Linux/Windows 或转换依赖可用性检查。

### 5.3 macOS

Seatbelt 是首版候选。profile 从默认拒绝开始，仅放行固定转换器及明确的运行依赖、调用输入、工作目录和必需系统资源。

- 文件读取规则不能代替进程执行规则；不得只限制二进制的读路径却无条件允许所有 process-exec。
- 动态库、字体、OCR 数据与必要系统服务逐项验证，不为了启动方便开放整个用户目录或任意 mach 服务。
- profile 路径必须转义、绝对化并校验；输入文件按文件粒度授权。
- 进程组用于基础终止，但不能声称它能约束任意重新建会话的后代。脱离进程组、应用崩溃及转换器衍生进程的处置必须实测。
- 若平台实现不能保证本阶段转换器的停止与回收，相关方法不得发布。Phase A 的测试结论不能直接作为任意 Shell 已安全可用的依据。

具体 profile 及系统版本支持范围在 A1 的实测结果中固化；本文不提供可直接复制为生产策略的示例。

### 5.4 Linux

bubblewrap 是候选，使用独立 mount/PID/network 环境、明确的只读输入与可写工作目录，并设置父进程退出处理及新会话隔离。以官方参数语义为准，不能仅凭命令退出成功判定隔离有效。

禁止默认把整个宿主用户目录暴露给进程。只读系统挂载与可执行二进制限制是不同边界，必须分别设计。资源整组限制优先探测可用的 cgroup v2 委派；不可用时不得宣称仍具有同等进程树资源配额。

缺少 bubblewrap、内核权限或必需的监督能力时，方法不可用并返回原因。Linux 单独验收，不假设与 macOS 同一参数具有同一含义。

### 5.5 Windows

Phase A 不提供外部转换，内置解析继续可用。前端明确显示平台限制；工具筛选与 Rust IPC 均拒绝不支持的方法。后续 Windows provider 需单独设计隔离和进程树控制，不降级到裸进程。

### 5.6 资源限制

预算由应用策略和任务计划共同决定，取较严格者。以下为初始评测预算，发布前需用代表性中文扫描件测定并记录调整结果。

| 资源 | 初始预算/实现要求 | 语义与平台边界 |
|---|---|---|
| 整次转换墙钟时间 | 120 秒，包含 PDF 渲染及 OCR 全部子步骤 | 由可信监督器计时；重试不重置任务总预算 |
| 单页像素 | 最多 2000 万像素，固定 DPI 且设尺寸上限 | PDF 渲染前检查，避免单页分配失控 |
| 单次页数 | 最多 20 页且不超过计划 maxPdfPages | 超限返回明确错误；分段转换另行定义，不能静默处理前 20 页 |
| 单进程 CPU | 候选 60 秒 | RLIMIT_CPU 不能当作整棵进程树的总预算 |
| 单进程内存 | 按平台 probe 结果选择可执行限制 | RLIMIT_AS 不等同整组内存；平台不支持时明确能力缺口 |
| 整组进程/内存 | Linux 优先 cgroup pids/memory；macOS 需验证监督策略 | 不把 RLIMIT_NPROC=64 当作“当前沙箱最多 64 个进程” |
| 单个输出文件 | 128 MiB | RLIMIT_FSIZE 仅限制单文件，不限制目录总量 |
| 工作目录总量 | 256 MiB，另设整实例临时空间预算 | 明确硬配额或监测实现及采样期间超额边界；监测不能宣传为硬配额 |
| stdout + stderr | 合计 1 MiB | 同时、增量读取计数，超限停止，不先收集后截断 |
| 重复转换 | 每文件每方法默认一次 | 显式重试需确认旧执行已终止，并计入 run/任务预算 |

Linux 的 RLIMIT_NPROC 按真实用户 ID 统计进程/线程，不是当前执行环境独享的计数器。平台限制语义参见 [getrlimit 官方手册](https://www.man7.org/linux/man-pages/man2/getrlimit.2.html)。

所有限制失败都返回独立 reasonCode。不能把内存、磁盘、语言包缺失统一显示为“文档无法读取”。依赖下载、OCR 数据加载、结果上传如另需预算，必须单列。

### 5.7 IPC 与调用步骤

拟新增 sandbox_extract_text、sandbox_cancel_execution 和 sandbox_capabilities 命令。取消请求绑定可信 task/run/call 身份；Rust 验证执行所有者，不提供可终止任意宿主 PID 的接口。executionId 由 Rust 在登记事件中返回，取消早于该事件时保留停止意图并阻止后续 spawn。

每次转换依次执行：

1. 检查当前平台/方法能力，验证任务运行状态、run、batchToken 和有效期。
2. 从数据库验证文件属于当前活动批次的 processing 项，并属于已确认计划。
3. 验证路径、普通文件类型、大小、mtime、SHA-256；提取本次调用的只读输入副本，见 §7。
4. 校验 method 与文件实际类型和依赖清单相容；映射为固定 argv 数组，不拼接 shell 命令。
5. 在同一批次的执行互斥区内，重新检查取消/租约状态，创建 executionId 并登记监督对象。
6. 在隔离环境中启动并监督渲染/OCR；不要在整个转换期间持有 SQLite 写事务。
7. 成功退出后校验结果大小、页数、完整性和 parser provenance；再次检查任务/租约以及是否已取消。
8. 返回结构化解析结果，完成回收与目录清理；模型随后通过既有 checkpoint 提交处理结果。

复制与启动之间必须有重新校验，避免暂停请求发生在输入准备期间却仍启动进程。租约不做无限续期；长调用只可在任务仍运行且登记归属有效时受限续租，取消和到期不得被续租覆盖。

## 6. TypeScript 接入与权限

### 6.1 工具契约

extract_document_text 的模型入参仅包含 batchToken、relativePath、method；首版 method 为 image_ocr、pdf_ocr。描述必须说明只用于已领取文件和读取结果提供的可用方法。

- readOnly: true：不修改用户源文件。
- concurrencySafe: false：避免同一调度轮并发；Rust 批次互斥仍是最终保证。
- destructive: false；计划范围内的 Phase A 不逐文件确认。
- permissions 包含 fs:read 和 process:spawn；availability 为 tauri-only，并额外检查方法能力。
- 工具超时必须大于 Rust 整次墙钟预算和终止宽限，例如初始 150 秒；应用硬限制或租约更短时使用更短有效预算。
- AbortSignal 必须触发 Rust 取消接口；Promise 超时只表示前端停止等待，不能当作底层进程已经退出。
- 不配置通用自动重试。readOnly 并不意味着没有临时目录/活动进程；受控重试必须在旧执行回收后进行。
- 返回原始文本之前执行后端字节限制；normalizeResult 的 handle 化不能替代资源限制。

大结果进入已有句柄存储，read_handle 必须在当前 batch 阶段可达。重启后若句柄失效，重新从受校验输入转换，不能假设旧内存句柄可恢复。

### 6.2 必须同时修改的接入点

| 接入点 | 拟调整 | 必要测试 |
|---|---|---|
| 工具注册及任务工具集合 | 注册工具并加入任务专用集合 | 普通聊天不可见；目标任务可见 |
| inventory、计划、入口判断 | 纳入可外部转换文件及依赖状态 | 仅图片任务可启动；不可用格式有解释 |
| 读取结果契约 | 引入 needs_external_parser 和可用方法 | 解析失败、依赖缺失与文件变化可区分 |
| loop-runtime 阶段名单 | batch 阶段增加转换工具及必要的 read_handle | 实际经历 context → plan → claim → read → extract → checkpoint |
| loop budget | 限制每文件/方法与整 run 的转换量 | 模型重复 OCR 被阻止 |
| PolicyEngine/ToolUseContext | 注入可信沙箱能力并保留用户拒绝优先级 | probe 失败、禁用工具、拒绝权限均不可执行 |
| checkpoint、状态统计与 UI | 接受依赖等待状态，提供重试与跳过 | 整批检查点完整；安装后不自动扩大旧计划 |
| Tauri handler 与状态管理 | 注册执行/取消/能力 IPC 和 ExecutionManager | 前端绕过不能突破 Rust 边界 |

不能只新增 FOLDER_TASK_TOOL_GROUPS.extract。当前 FOLDER_TASK_STAGE_TOOLS.batch 有独立的名称白名单，漏改会让工具在真正需要调用时不可见。

### 6.3 进程权限与 Phase B 的边界

PolicyEngine 只对运行时代码确定的沙箱工具解除 process:spawn 的默认拒绝，并继续执行用户禁用、权限拒绝及常规确认策略。方法能力、可信调用身份及文件边界还必须在 Rust 复核。

Phase B 必须同时满足：全局启用开关、当前契约/阶段显式授权、工具可用性探测和用户确认。Agent 模式当前没有“未在契约声明的工具一律不可用”的通用保证，因此应显式排除 run_shell，而不是仅在 generationCapabilities 中增加名称。

Phase B 初版若要求每次命令确认，需禁止该工具的“本 run 总是允许”捷径；不能复用现有会话授权分支后仍声称每次确认。后续若支持目录级或命令类别授权，应另写授权语义。

FolderTask 的 batchToken 不适用于没有批次的普通交付物契约。Phase B 需要定义自己的可信工作范围如何映射到现有会话/契约权限；不能伪造批次或把全工作区直接作为默认输入。这部分在 B1 前单独评审。

## 7. 输入快照与文件视图

### 7.1 按调用暂存

撤销“不复制输入”的硬约束。只暂存当前调用所需文件，不预复制整个任务目录。受信任的输入暂存不是写回用户文件，也不引入第二条用户文件写入路径。

- 在应用专属、随机且权限受限的临时实例目录下建立 execution 子目录。
- input 存放受信任父进程创建的输入副本，对子进程只读；work 是唯一可写目录。两者不可被同一条宽泛写规则覆盖。
- 从已打开并检查的源文件读取到副本，复制过程中计算 SHA-256；验证复制内容与 inventory 哈希一致，核对复制前后元数据。
- 使用独占创建，拒绝符号链接/特殊文件，避免临时路径被预置替换。
- 转换器只收到暂存路径；来源中保留原 relativePath、inventory fingerprint、内容哈希及转换方法版本。

父进程负责构建 input；即使源文件在复制完成后变化，本次处理也明确对应已确认内容。需要处理新版本时，重新扫描并确认，不能悄悄更换来源。

### 7.2 结果回流

Phase A 只回传有界文本、页信息和来源。PDF 渲染图片等中间文件不进入用户工作区，所有成功处理仍走原来的模型结果契约和确定性输出。

Phase B 的 import_sandbox_artifact 必须检查产物归属、普通文件类型、目标路径、覆盖策略和实际导入内容，内部走受约束的写入路径，并返回可审阅的产物信息。任意临时路径不构成写回授权。

## 8. 执行、取消与恢复

### 8.1 执行登记与时序

ExecutionManager 至少维护 preparing、running、stopping、finished 状态；从输入暂存开始接受取消。批次取消标记、登记和启动检查需同步，避免“取消时还没有进程，因此稍后又启动”的竞态。

~~~text
调用 → 登记准备意图 → 校验/暂存 → 复核租约 → 启动 → 监督 → 复核结果 → 返回
                 ↑                       │
任务暂停/取消、run abort、租约到期、超时 ──┘
                 ↓
             标记 stopping
                 ↓
阻止新执行/续租 → 请求停止 → 短宽限后强制终止 → 等待进程树回收
                 ↓
丢弃晚到结果 → 释放批次未提交项 → 清理本次临时目录 → 发布终止状态
~~~

任务停止意图应立即阻止新 claim 与新执行；对外确认“已停止”须在回收后完成。终止失败时显示停止异常并保留隔离/互斥状态，不能让同一批次重新启动覆盖旧执行。

检查点与活动转换不能竞态提交：Rust 必须拒绝在本批次仍有活动转换时完成 checkpoint，或先按确定顺序等待转换回收。整个 run 的自动重试同样不能绕过这一门槛。

### 8.2 应用退出和崩溃

正常退出按取消时序停止并回收。异常退出需要平台提供可验证的父死亡处置或监督机制；启动时删目录不能终止遗留进程。

临时目录以随机 appInstanceId / executionId 隔离。清理只针对已确认属于本实例或无活跃所有者的旧目录，拒绝符号链接，不递归删除其他仍运行实例的目录。不得根据未经验证的旧 PID 杀进程，以免 PID 已复用。

恢复时丢弃临时执行状态，沿用批次恢复规则重领未提交项；已持久化的文件结果保留。无需为了沙箱新增容器快照或 session 数据库，但取消、批次释放、句柄失效和 run 恢复的接入代码及测试必须调整，不能提前承诺 recovery/snapshot/run-state 完全不变。

### 8.3 日志

记录 executionId、任务/批次/run、method、组件版本、sourceHash、开始/终止原因、退出码、耗时、输出量和资源限制命中情况。避免记录 batchToken、文档全文和未经脱敏的 stderr。

Phase B 的 argv/命令可能含用户内容和凭据，默认不写入完整命令到通用日志；审批展示与诊断留存需分别定义访问范围。

## 9. OCR 流水线与依赖交付

### 9.1 固定执行流程

| 方法 | 流程 | 完整性要求 |
|---|---|---|
| image_ocr | 验证类型/尺寸 → Tesseract → 文本与告警 | 拒绝超尺寸、损坏及不支持的图片；记录语言包 |
| pdf_ocr | 检查 PDF 页数/加密 → 固定 PDF 渲染器逐页渲染 → 每页 Tesseract → 按页合并 | 页码可追溯；任何失败页/截断必须可见 |

Tesseract 不直接读取 PDF，参见 [官方输入格式说明](https://github.com/tesseract-ocr/tessdoc/blob/main/InputFormats.md)。首版需要明确的 PDF 渲染器（例如评估固定版本的 pdftoppm），不能用一个未定义的 tesseract_wrapper 占位后宣称扫描 PDF 已支持。

PDF 渲染、OCR 和合并共享同一次执行的总预算；逐页处理和删除中间图像，避免全部页面同时展开。渲染器解析不可信 PDF，也必须在隔离范围内。encrypted、page_limit、render_failed、ocr_failed、dependency_missing 分开报告。

### 9.2 依赖交付门槛

A0 必须选择并记录组件分发方式，不能推迟到端到端验收之后：

- 开发验证可使用显式配置的本机固定绝对路径，记录版本；不按模型输入或任意 PATH 查找。
- 面向用户的默认候选是独立可选组件包，由受信任安装器在用户触发后安装；沙箱转换过程本身不下载组件。
- 若采用随包分发，需同样提供组件清单、许可证、版本锁定、完整性校验、平台架构、签名/公证验证及升级回滚方案。
- OCR 组件必须包含所声明语言（首版中文简体和英文）的数据、渲染器及其动态依赖。
- UI 区分未安装、安装中、就绪、版本/完整性异常；组件移除或失效后重新探测并停止暴露对应方法。
- 最终选择以包体积、授权许可、目标平台签名与离线可用性评测为依据。A0 未定稿不进入 A3 用户验收。

## 10. 实施顺序与平台验收

### 10.1 实施顺序

| 阶段 | 交付 | 退出条件 |
|---|---|---|
| A0 | 状态/接口契约、依赖方案与平台预算验证 | 首版组件、语言、支持系统及限制有明确记录 |
| A1 | macOS provider、输入暂存、ExecutionManager | 越界、取消、崩溃回收和快照测试通过 |
| A2 | 固定 OCR 流程、Rust IPC、批次互斥 | 图片和扫描 PDF 转换成功，失败分类与终止可验证 |
| A3 | 扫描/计划/工具名单/权限/UI/检查点接入 | 从新建任务到最终结果完整跑通，旧任务可显式恢复 |
| A4 | Linux provider 与依赖包 | 独立通过平台矩阵，不沿用 macOS 结论 |
| B1 | Shell 范围与命令执行契约评审后实现 | 显式授权、默认不可见、取消及任意子进程测试通过 |
| B2 | 产物导入与用户交付 | 范围、内容、覆盖和来源可审阅 |
| C | 企业/CI 的其他 provider | 有具体需求再启动 |

### 10.2 平台验收矩阵

| 验收项 | macOS Phase A | Linux A4 | Windows Phase A |
|---|---|---|---|
| 图片/扫描 PDF + 中文英文文本 | 正向端到端必过 | 同套样本独立验证 | 显示外部转换不可用 |
| 文件范围 | 无法读取其他文档、宿主凭据、未领取文件 | 同左 | IPC 拒绝 |
| 写入范围 | 只能写本调用 work，不能改 input、源文件、.solidify、.git | 同左 | IPC 拒绝 |
| 网络 | TCP/UDP 等外联及代理路径均不可突破策略 | 同左 | 不启动 |
| 快照 | 扫描后改文件、暂存时改文件、符号链接替换均被拒绝或绑定已验证副本 | 同左 | 不启动 |
| 租约 | 伪造 token、跨 run、过期与暂停后调用均拒绝 | 同左 | 不启动 |
| 取消与回收 | 暂停、超时、退出、崩溃、子进程/后台进程均无越权残留 | PID 环境/父死亡处置独立验证 | 不启动 |
| 资源 | 正常文档可用；输出/页数/空间限制触发可解释；记录硬限制与监测边界 | 额外验证 cgroup 不可用的降级决策 | 不启动 |
| 安装 | 缺组件、缺语言包、组件损坏、升级回滚可反馈 | 同左 | 保留内置解析 |
| 多实例 | 一个实例不清理/终止另一个实例的执行 | 同左 | 不适用 |

破坏性资源测试只能在专用测试环境使用有上限的夹具，不能对开发者宿主直接运行无界 fork/磁盘填充负载。

### 10.3 产品与恢复验收

1. 仅图片文件夹可以预览 OCR 范围并启动；混合输入不因一份损坏文件阻塞其他文件。
2. 扫描 PDF 内置读取不足时，在同一批次调用外部转换；模型能读取大文本句柄并提交完整 checkpoint。
3. 缺依赖时显示可操作原因；安装后旧任务由用户重试，已排除文件须重新确认范围。
4. 取消发生在暂存前、启动前、运行中、成功返回前均有效；晚到结果不能进入 checkpoint。
5. 重启后已提交结果保留，未提交项重新领取，临时文件/旧句柄不成为恢复依赖。
6. 越界工具调用即使绕过前端也被 Rust 拒绝；普通聊天及未授权阶段看不到转换/Shell 工具。
7. 最终输出能追溯原文件哈希、OCR 方法、版本、页数和部分失败，不能只以 awaitingExternalParser 归零作为成功标准。

## 11. 非目标与待决事项

Phase A 不提供任意 Bash/Shell、旧 Office、压缩包转换、网络访问、Windows 外部执行、容器持久化或 Shell 写检查点。暂不要求用户安装 Docker。

A0 待决项：PDF 渲染器和具体组件版本、组件包分发路径、macOS 支持系统范围、每个平台的进程树终止与资源限制实现。每项都需要负责模块、可复现验证与发布阻断条件，不能用“后续实测”代替交付标准。

Phase B 仍保留为后续阶段，进入前另行评审非批次契约的文件授权、Shell 运行环境、命令确认策略、取消边界和产物导入。不把“先完成 OCR”解释为已经实现模型通用文件操作能力。

参考：[bubblewrap 官方项目](https://github.com/containers/bubblewrap)、[Linux getrlimit](https://www.man7.org/linux/man-pages/man2/getrlimit.2.html)、[Tesseract 输入格式](https://github.com/tesseract-ocr/tessdoc/blob/main/InputFormats.md)。
